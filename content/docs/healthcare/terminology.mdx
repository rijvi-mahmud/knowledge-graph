---
title: Terminology
description: 'The code systems the hospital uses, such as ICD-10-CM, ICD-11, SNOMED CT, LOINC and UCUM: their releases and effective dates, value sets, maps between them, and checking a code on a date.'
module: terminology
version: 0.1.0
status: draft
industry: healthcare
purpose: Give every module one place to ask whether a code is valid on a date, what it means, which codes a field allows, and what it maps to. Load each release of each code system with its effective dates, check it before use, and keep every release ever used, so records coded years ago stay readable. Works in the United States and the European Union.
scope:
- A catalogue of the code systems in use, with their identifiers, publishers, licences and editions
- Loading, checking, activating and withdrawing releases, with the dates each one is in effect
- Checking a code on a date against the release in effect then, including whether it is valid for reporting
- Looking up displays in each language, properties, parents and children
- Inactive and replaced codes, with the replacements their publishers name
- 'Value sets: the codes a field allows, versioned and bound to the module settings that use them'
- Maps between code systems, including rule-based maps that need the patient's age or sex, and translation
- ICD-11 postcoordination clusters
- Local codes in the hospital's own code systems
- Dual coding while moving from one classification to another, such as ICD-10 to ICD-11
- 'Licences: loading and showing licensed content only where the hospital holds the licence'
- Watching for releases that are due
nonGoals:
- 'The content of code systems. Their publishers own it: WHO, CDC and CMS, SNOMED International, Regenstrief, NLM, the AMA and national bodies.'
- Choosing codes for a claim, payer code edits and grouping. Billing owns coding.
- Recording diagnoses, results or medications. Each module records its own codes and asks this module whether they are valid.
- Automatic coding from free text, including by AI.
- Negotiating licences. The hospital holds them; this module records them.
- Clinical decision rules built on codes. Clinical decision support owns them.

- name: Clinician

assumptions:
- id: AS-H1
  text: Publishers distribute releases as files the hospital can download, with dates of effect, and checksums or record counts to check them against.
  rationale: CDC, CMS, NLM, SNOMED International, Regenstrief and WHO publish release files and notes with each release.
- id: AS-H2
  text: Callers send the date a code applies to, and the patient context a rule-based map needs.
  rationale: Which release applies depends on the date of care, and map rules depend on the patient's age and sex. This module holds no patient data.
- id: AS-H3
  text: The hospital holds the licences for the code systems it uses, such as the AMA's for CPT.
  rationale: Some code systems can't be used without a licence; others are free with attribution.
glossary:
- term: Code system
  definition: A set of codes with meanings, such as ICD-10-CM or LOINC, identified by a URI (FHIR CodeSystem).
- term: Release
  definition: One version of a code system, in effect from one date to another.
- term: Classification
  definition: A code system that groups conditions into mutually exclusive categories for statistics and payment, such as ICD.
- term: Value set
  definition: The codes a field allows, defined by rules over one or more code systems (FHIR ValueSet).
- term: Map
  definition: Links from codes in one code system to codes in another, with how closely each matches (FHIR ConceptMap).
- term: Stem code
  definition: An ICD-11 code that can be used alone.
- term: Extension code
  definition: An ICD-11 code that adds detail, such as laterality or severity, to a stem code and is never used alone.
- term: Cluster
  definition: 'ICD-11 codes joined into one: stem codes with a slash (/), extension codes with an ampersand (&).'
- term: Dual coding
  definition: Coding the same thing in two classifications or versions, for example during a transition (WHO).
- term: Header code
  definition: An ICD-10-CM or ICD-10-PCS code that heads a group and isn't valid for reporting.
concepts:
- name: A code means what its release says
  description: A code is checked against the release in effect on the date it applies to. A record keeps the system, code and release, so it reads the same years later even after the code is inactivated.
- name: Translation suggests, never replaces
  description: A map returns candidate codes and how closely they match. The original code always stays in the record.

businessRules:
- id: BR-H1
  text: A code is identified by its code system URI and code, never by its display. Every module records the system, the code and the release version it validated against. The code systems and editions in use are those in code_systems_in_use.
  rationale: Displays change between releases and languages; the code doesn't. With the release recorded, a record reads the same years later.
- id: BR-H2
  text: A code is checked against the release of its code system in effect on the date the caller gives. At most one release of a code system and edition is in effect on any date.
  rationale: HIPAA code sets are valid only within the dates their maintainers set (45 CFR 162.1011), and CDC states the range of dates of care each ICD-10-CM release applies to.
- id: BR-H3
  text: 'Callers choose the date by code_date_rule: by default the date of service. For ICD-10-CM and ICD-10-PCS on US inpatient claims, the discharge date.'
  rationale: CDC states its releases by date of service, while CMS has institutional claims use the code set in effect on the discharge or through date (MLN Matters SE1408). The sources differ by use, so it is a setting.
- id: BR-H4
  text: 'A new release is staged, then verified: its checksum or record counts match what the publisher states, its files parse, and the changes from the previous release are listed. Only a verified release can be activated.'
  rationale: A truncated or corrupt release would silently reject valid codes or accept invalid ones in every module at once.
- id: BR-H5
  text: A Terminology manager activates a verified release, which takes effect on its effective_from date and sets the previous release's effective_to to the day before. A release can be activated before its date, so it is ready in time. Activation is all or nothing.
  rationale: ICD-10-CM releases are published ahead of 1 October and any 1 April update. Loading ahead means validation switches over on the right day without anyone working at midnight.
- id: BR-H6
  text: 'Releases are never deleted or changed once active. A release its publisher recalls is withdrawn: dates it covered fall back to the previous release, and codes recorded against it stay readable.'
  rationale: Records coded against a release must stay readable for as long as they are kept.
- id: BR-H7
  text: When no release covers the date given, validation answers unknown rather than invalid, and names the dates the loaded releases cover.
  rationale: A record from before the hospital loaded a code system isn't wrong; the caller decides whether to accept it.
- id: BR-H8
  text: An inactive code is never valid for new use on a date it is inactive, but stays readable with its last display. Validation returns the replacements its publisher names. Recorded codes are never rewritten automatically.
  rationale: SNOMED CT links inactive concepts to active ones through historical associations, and LOINC names a replacement in MAP_TO. Which replacement is right depends on the record, so a person or the owning module decides.
- id: BR-H9
  text: 'Codes are matched exactly as the code system defines: by case only where it is case-sensitive, as UCUM is. Input is normalized only by a code system''s own documented rules.'
  rationale: UCUM defines case-sensitive symbols, and mg and Mg are different. Guessing at normalization turns a typo into a different code.
- id: BR-H10
  text: A code that fails its code system's check digit (SNOMED CT Verhoeff, LOINC mod 10) and isn't in the release is reported as a likely typing error. Presence in the release decides validity.
  rationale: SNOMED CT identifiers end in a Verhoeff check digit and LOINC codes in a mod 10 check digit; LOINC lists a few terms whose check digits are known to be wrong, so the digit alone mustn't reject a code.
- id: BR-H11
  text: Validation says separately whether a code exists, is active, and is valid for reporting. ICD-10-CM and ICD-10-PCS header codes exist but aren't valid for reporting.
  rationale: The ICD-10-CM and ICD-10-PCS order files flag header codes as not valid for HIPAA-covered transactions. A diagnosis can be recorded clinically before it is coded fully for a claim.
- id: BR-H12
  text: An ICD-11 cluster is valid only when each part is valid in the release, stem codes are joined by a slash and extension codes by an ampersand, and no extension code is first or alone.
  rationale: The ICD-11 reference guide defines clusters this way and says extension codes can never be used without a stem code or first in a cluster.
- id: BR-H13
  text: A module's coded setting, such as encounter_type_codes, is bound to a value set here. Each change makes a new version; an active version never changes.
  rationale: Records validated against a value set must be explainable later. FHIR versions value sets for the same reason.
- id: BR-H14
  text: A value set is expanded on a date, using for each rule the release named or the release in effect on that date. With a required binding, codes outside it are refused; with an extensible one, a code outside it is allowed only when no code in it fits, with text.
  rationale: FHIR defines required and extensible bindings this way. Expanding on the date keeps a value set over ICD-10-CM in step with each year's release.
- id: BR-H15
  text: Translating a code returns candidate targets with their relationship and never replaces the source code in any record.
  rationale: Maps are rarely one to one. FHIR ConceptMap says how closely each target matches; the record keeps what the clinician chose.
- id: BR-H16
  text: A rule-based map, such as SNOMED CT to ICD-10-CM, evaluates its rules with the patient context the caller sends, such as age and sex. When the context is missing, every candidate is returned, flagged for a person to choose. The context is never stored.
  rationale: NLM's SNOMED CT to ICD-10-CM map uses rules on age and sex; for example, sleep apnea maps to a newborn code or another depending on age. Keeping no context means this module holds no patient data.
- id: BR-H17
  text: Year-to-year ICD-10-CM changes are followed with the CDC conversion table. CMS GEMs, last updated for fiscal year 2018, are used only for ICD-9 history.
  rationale: CDC publishes a conversion table with each ICD-10-CM release, and CMS stopped updating GEMs after fiscal year 2018.
- id: BR-H18
  text: ICD-10 to ICD-11 translation uses the transition tables WHO publishes with each ICD-11 version, and ICD-11 releases are loaded with their version identifiers.
  rationale: WHO releases ICD-11 in versions with identifiers used when reporting, and provides transition tables with every version.
- id: BR-H19
  text: During a transition set in dual_coding, a field can hold a code from each classification in the pair, each validated against its own release.
  rationale: WHO describes dual coding for transitions and comparison. Countries move from ICD-10 to ICD-11 at different times, and statistics need both during the change.
- id: BR-H20
  text: Local codes live only in local code systems under local_namespace, never added to a standard code system. A local code used in a field that is exchanged must map to a standard code, or it is flagged.
  rationale: A local code under a standard URI would be read as a standard code by every receiver. SNOMED CT extensions need a namespace from SNOMED International.
- id: BR-H21
  text: A release can be activated only when its code system's licence is recorded as held or the content is free. Licensed content, such as CPT descriptions, is shown only to callers within the licence, and every display carries the attribution the licence requires.
  rationale: The AMA requires a licence to use or display CPT content; SNOMED CT is free in member countries such as the United States under the affiliate licence; LOINC and ICD-11 are free with conditions, ICD-11 under CC BY-ND 3.0 IGO.
- id: BR-H22
  text: Displays are returned in the language asked for when the release has one, and otherwise in default_language, or the code system's preferred display, marked as a fallback.
  rationale: National editions and translations carry their own displays; a patient or clinician must never see a blank where a code's meaning should be.
- id: BR-H23
  text: Search by text looks in displays and synonyms of a value set's expansion on a date, returns active codes only unless asked, and never returns content the caller's licence excludes.
  rationale: Clinicians find codes by words. Returning inactive codes for new entries would bring retired codes back.
- id: BR-H24
  text: For each code system in release_watch, a release not loaded by its warning date is listed, and terminology.release_overdue is emitted.
  rationale: ICD-10-CM changes every 1 October and sometimes 1 April, LOINC publishes in February and August, and SNOMED CT's International Edition and RxNorm publish monthly. A missed release means valid new codes are refused.
- id: BR-H25
  text: Activating, withdrawing or retiring a release, a value set or a map emits an event with the changes, so modules can re-check settings and open records that use them.
  rationale: Modules cache code lists. Without an event they keep refusing new codes or accepting retired ones.
- id: BR-H26
  text: Every load, verification, activation, withdrawal and change to a value set, map or local code is logged with who, when and why.
  rationale: Coding drives claims and statistics; an auditor must be able to see why a code was accepted on a date.
- id: BR-H27
  text: Every answer names the releases and value set versions it used.
  rationale: A caller caching an answer, or explaining a decision later, needs to know which release it came from.
- id: BR-H28
  text: 'Requests are never refused for another module''s reasons: validation answers on the codes and dates given.'
  rationale: Each module owns its own rules about which codes it accepts; this module only says what a code means and whether it is valid.
- id: BR-H29
  text: 'In the United States, the code sets for HIPAA transactions are loaded: ICD-10-CM for diagnoses, ICD-10-PCS for inpatient procedures, HCPCS and CPT for other services, CDT for dental services and NDC for retail pharmacy drugs. For certified health IT, SNOMED CT US Edition and LOINC are loaded at the versions ONC names.'
  rationale: HIPAA names these code sets (45 CFR 162.1002), and ONC names vocabulary standards for certified health IT (45 CFR 170.207).
  jurisdiction: us
- id: BR-H30
  text: In the European Union, value sets for fields exchanged in the European electronic health record exchange format use the coding systems its implementing acts name, as they are updated.
  rationale: The EHDS exchange format includes coding systems and values, laid down and updated by implementing acts (Article 15).
  jurisdiction: eu
- id: BR-H31
  text: Concurrent changes to a value set, map or local code send the revision they read; a stale revision fails.
  rationale: Two Terminology managers editing one value set must not overwrite each other.
- id: BR-H32
  text: Validation, lookup and expansion keep working from the active releases when release sources or downloads are unreachable; only loading needs them.
  rationale: Every module depends on validation. A publisher's site being down must never stop care being recorded.
validations:
- field: code_system.uri
  rule: An absolute URI; local systems start with local_namespace; not already registered
  error: TERMINOLOGY_INVALID_CODE_SYSTEM
- field: code_system.licence
  rule: Names the licence and whether it is held, or that the content is free
  error: TERMINOLOGY_INVALID_CODE_SYSTEM
- field: release.version
  rule: Unique for its code system
  error: TERMINOLOGY_RELEASE_EXISTS
- field: release.effective_from
  rule: A date; not inside an active release's period of the same edition unless that release is superseded by it
  error: TERMINOLOGY_RELEASE_OVERLAP
- field: release.source
  rule: Files whose checksum or record counts match the publisher's, and that parse
  error: TERMINOLOGY_RELEASE_VERIFICATION_FAILED
- field: value_set.rules
  rule: Each rule names a registered code system and a valid filter or listed codes present in the release it names
  error: TERMINOLOGY_INVALID_VALUE_SET
- field: map.entries
  rule: Each source and target code exists in the releases the map names, and each relationship is a ConceptMap relationship code
  error: TERMINOLOGY_INVALID_MAP
- field: concept.code
  rule: Added only to local code systems, unique in them
  error: TERMINOLOGY_LOCAL_CODE_NOT_ALLOWED
- field: release.status
  rule: Fields the service sets, such as status, effective_to, changes and releases, can't be written by clients
  error: TERMINOLOGY_READ_ONLY_FIELD
stateMachine:
  initial: staged
  states:
  - staged
  - verified
  - active
  - retired
  - withdrawn
  transitions:
  - from: staged
    to: verified
    trigger: verify (BR-H4)
    guard: checksum or counts match and files parse
  - from: staged
    to: withdrawn
    trigger: discard a staged release
  - from: verified
    to: active
    trigger: activate (BR-H5)
    guard: licence held or free (BR-H21)
  - from: verified
    to: withdrawn
    trigger: discard a verified release
  - from: active
    to: retired
    trigger: a later release takes over and its effective date passes
  - from: active
    to: withdrawn
    trigger: the publisher recalls it (BR-H6)
workflows:
- name: Load a new release
  trigger: A publisher releases a new version, or release_watch lists one as due
  actor: Terminology manager
  steps:
  - Stage the release from the publisher's files
  - 'Verify it: checksums or counts, parsing, and the list of changes'
  - Review the changes, especially codes inactivated that value sets or settings use
  - Activate it, effective on the publisher's date
  - terminology.release_activated is emitted with the changes
  outcome: Validation uses the new release from its effective date, and modules know what changed.
- name: Validate a code
  trigger: A module records a coded value
  actor: System
  steps:
  - Send the system, code, date and optionally a value set
  - The service finds the release in effect on the date, and the value set expansion
  - It answers valid, invalid, inactive or unknown, with valid_for_reporting, the display and any replacements
  outcome: The module accepts or refuses the code with a reason, and records the release used.
- name: Change a value set
  trigger: A module's setting needs other codes
  actor: Terminology manager
  steps:
  - Create a new draft version with the changed rules
  - Expand it on today's date and review it
  - Activate it; terminology.value_set_activated is emitted
  outcome: The setting uses the new version; records validated against the old one keep its version.
- name: Move to ICD-11
  trigger: A country adopts ICD-11 for a use
  actor: Terminology manager
  steps:
  - Load the ICD-11 MMS release and WHO's transition tables
  - Set dual_coding for the period
  - Bind the value sets to ICD-11 from the adoption date
  outcome: Both classifications are coded during the transition, and ICD-11 alone after it.

apiConventions:
- topic: Authentication
  text: Every request carries the caller's identity from Identity. Permissions are checked against it (Permission matrix).
- topic: Errors
  text: Errors use problem details (application/problem+json) with a code member, such as TERMINOLOGY_RELEASE_OVERLAP. A validation that finds a code invalid is a 200 with the result, not an error.
  reference: RFC 9457
- topic: Pagination
  text: 'Lists and expansions are cursor-based: limit and an optional cursor in, next_cursor out.'
- topic: Concurrency
  text: Every change sends the revision it read. A stale revision fails with TERMINOLOGY_REVISION_CONFLICT (BR-H31).
- topic: Retries
  text: Every create accepts an Idempotency-Key header; a retry returns the original result.

Every module that records a diagnosis, a test or a unit asks this one what
the code means and whether it is allowed. It holds each release of each code
system with the dates it applies to, so the answer depends on when the care
happened, not on when someone asks.

## A code is checked against the release in effect on the day

ICD-10-CM changes every 1 October and sometimes on 1 April, LOINC twice a
year, and SNOMED CT's International Edition every month. A code valid last
September may not be valid now, and the reverse. So every validation names a
date, and the answer names the release it used (BR-H2, BR-H27). Which date to
use is a setting, because CDC states releases by date of service while CMS
uses the discharge date for inpatient claims (BR-H3).

## Nothing is ever deleted

Releases are added, never changed or removed, and inactive codes keep their
meaning. A record coded in 2016 reads the same today, and the publisher's
suggested replacement is offered without rewriting it (BR-H6, BR-H8).

## A map suggests, a person decides

Maps between code systems are rarely one to one. A translation returns
candidates and how closely each matches, uses the patient's age or sex only
for the request, and never replaces the code a clinician chose (BR-H15,
BR-H16).

## A late release is everyone's problem

When a new release isn't loaded on time, valid new codes are refused in every
module at once. The service watches for releases that are due, and a release
can be loaded weeks ahead to take effect on its own date (BR-H5, BR-H24).
