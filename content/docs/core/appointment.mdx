---
title: Appointment
description: The scheduling lifecycle - booking, rescheduling, cancellation, reminders and attendance - specified in industry-neutral terms.
module: appointment
version: 0.2.0
status: stable

purpose: Own the lifecycle of a reserved time slot between participants, independent of what the appointment is for.
scope:
  - Book, reschedule, cancel and complete an appointment, and record a no-show
  - Own the status lifecycle and its legal transitions
  - Prevent overlapping appointments for the same participant
  - Store times so they stay correct across time zones and daylight saving changes
  - Schedule reminders relative to the start time
  - Emit lifecycle events other modules react to
nonGoals:
  - Owning participant identity - that belongs to the Identity module
  - Owning payment or billing - that belongs to the Billing module
  - Owning what happens during the appointment, such as notes or outcomes
  - Computing availability, working hours, buffers or minimum booking notice - Appointment asks Calendar
  - Recurring series - see open questions
  - Delivering notifications - Appointment emits reminder_due and Notification delivers it

actors:
  - name: Requester
    description: Party who initiates a booking. May be a participant or someone acting on their behalf.
  - name: Participant
    description: Party expected to attend. Every appointment has at least two.
  - name: Scheduler
    description: Operator with elevated rights to book, move, cancel or close out appointments on behalf of others.
  - name: System
    description: Automated actor that dispatches reminders and, where enabled, records no-shows after a grace period.

glossary:
  - term: Slot
    definition: A half-open time range [start, end) that an appointment reserves. The end instant is not part of the slot.
  - term: Active appointment
    definition: An appointment in status booked. Only active appointments hold their slot.
  - term: No-show
    definition: An appointment that a participant did not attend, recorded after its start time.
  - term: Reminder offset
    definition: Duration before the start time at which a reminder is dispatched.
  - term: Revision
    definition: A counter that increases each time an appointment's time changes. Equivalent to SEQUENCE in iCalendar (RFC 5545).
  - term: Wall-clock time
    definition: The local date and time participants see, such as 09:00 on 3 March, interpreted in a named time zone.

concepts:
  - name: Appointment
    description: A reserved time slot between two or more participants, with a status lifecycle.
  - name: Participant
    description: An identity taking part in the appointment, with a role such as host or guest. Industry layers define their own roles.
  - name: Reminder
    description: A scheduled notification derived from the appointment. Not independently bookable.
  - name: Reschedule
    description: A time change that keeps the appointment's id and history and increases its revision, rather than creating a new appointment.

dataModel:
  - name: id
    type: string
    required: true
    description: Stable identifier, immutable for the life of the appointment.
  - name: participants
    type: 'array<{ identity_id, role }>'
    required: true
    description: The parties involved. role is a label such as host or guest; industry layers define their own roles.
    constraints: at least 2 entries; identity_id values are distinct and resolvable
  - name: start_time
    type: local datetime
    required: true
    description: Wall-clock start in time_zone.
    constraints: before end_time
  - name: end_time
    type: local datetime
    required: true
    description: Wall-clock end in time_zone. Exclusive - the slot ends immediately before this time.
    constraints: after start_time
  - name: time_zone
    type: string
    required: true
    description: IANA time zone name in which start_time and end_time are interpreted, for example Europe/Zurich.
    constraints: a valid IANA tz database name, not a UTC offset
  - name: start_at
    type: instant
    required: true
    description: Absolute start, derived from start_time and time_zone. Used for overlap checks, reminders and ordering.
    constraints: derived, never written by clients; recomputed when tz database rules change
  - name: end_at
    type: instant
    required: true
    description: Absolute end, derived from end_time and time_zone.
    constraints: derived, never written by clients
  - name: status
    type: enum
    required: true
    description: Current lifecycle state.
    constraints: booked | cancelled | completed | no_show
  - name: revision
    type: integer
    required: true
    description: Starts at 0 and increases by 1 on every reschedule. Clients send it back to detect concurrent changes.
  - name: location
    type: string
    required: false
    description: Physical address or virtual meeting reference.
  - name: reminder_offsets
    type: duration[]
    required: false
    description: When reminders fire, each measured back from start_at.
    constraints: each offset positive; defaults to [24h]
  - name: notes
    type: string
    required: false
  - name: created_at
    type: instant
    required: true
  - name: updated_at
    type: instant
    required: true
  - name: cancelled_reason
    type: string
    required: false
    constraints: required when status = cancelled
  - name: cancelled_by
    type: string
    required: false
    description: Identity id of the actor who cancelled.
    constraints: set when status = cancelled
  - name: cancelled_at
    type: instant
    required: false
    constraints: set when status = cancelled
  - name: completed_at
    type: instant
    required: false
    constraints: set when status = completed
  - name: no_show_recorded_by
    type: string
    required: false
    description: Identity id of the Scheduler who recorded the no-show, or system.
    constraints: set when status = no_show

relationships:
  - type: belongs_to
    target: calendar
    note: every appointment sits on exactly one calendar
  - type: has_many
    target: reminder
    note: one per entry in reminder_offsets
  - type: requires
    target: identity
    note: every participant identity_id must resolve to an identity
  - type: can_trigger
    target: 'event:appointment.reminder_due'
  - type: requires_permission
    target: appointment.write

businessRules:
  - id: BR-1
    text: An appointment must have at least two distinct participants.
    rationale: A single-party slot is a calendar block, not an appointment. Keeping them distinct stops this module absorbing calendar concerns.
  - id: BR-2
    text: Cancelling never deletes the record. It sets status = cancelled and records who cancelled, when and why.
    rationale: Billing, audit and analytics hold references to the appointment id and break on hard delete. Cancellation reasons are also the main input for reducing late cancellations.
  - id: BR-3
    text: Rescheduling keeps the appointment id, increases revision by 1 and records the previous times in the appointment's history. It never creates a new appointment.
    rationale: Attendance and no-show statistics must follow one appointment across time changes. Cancel-and-rebook would count every reschedule as a cancellation.
  - id: BR-4
    text: A participant cannot have two active appointments whose slots overlap. Slots are half-open, so an appointment ending at 10:00 and one starting at 10:00 do not overlap.
    rationale: Double booking is a data-integrity failure, not a user preference, so it must hold under concurrent requests. Treating the end as inclusive would reject every back-to-back schedule.
  - id: BR-5
    text: Completed, cancelled and no_show are terminal. An appointment in a terminal state never changes again.
    rationale: Terminal states let downstream consumers treat the record as immutable and cache it without invalidation.
  - id: BR-6
    text: Times are stored as wall-clock time plus an IANA time zone. Absolute instants are derived from them, and recomputed for future appointments when time zone rules change.
    rationale: Participants agree to 09:00 local time, not to a UTC instant. Governments change daylight saving rules with little notice, and an instant computed before the change would move the appointment.
  - id: BR-7
    text: A reminder whose dispatch time has already passed when the appointment is booked or rescheduled is skipped. It never causes the booking to fail.
    rationale: With a 24-hour default, rejecting such bookings would block every same-day appointment. The remaining reminders still fire.
  - id: BR-8
    text: A no-show can be recorded only after the appointment's start time. By default a Scheduler records it; automatic recording after a grace period is a per-deployment setting.
    rationale: Leading scheduling products record no-shows manually, because only staff know whether someone is running late, attended remotely or was seen elsewhere. A wrongly recorded no-show is terminal and can trigger fees.

validations:
  - field: start_time
    rule: must be strictly before end_time
    error: APPOINTMENT_INVALID_TIME_RANGE
  - field: start_time
    rule: start_at must be in the future when booking or rescheduling
    error: APPOINTMENT_START_IN_PAST
  - field: start_time
    rule: must exist in time_zone; a wall-clock time skipped by a daylight saving change is rejected
    error: APPOINTMENT_INVALID_LOCAL_TIME
  - field: time_zone
    rule: must be a valid IANA time zone name
    error: APPOINTMENT_INVALID_TIME_ZONE
  - field: participants
    rule: at least 2 entries, all resolvable identity ids, no duplicates
    error: APPOINTMENT_INVALID_PARTICIPANTS
  - field: reminder_offsets
    rule: every offset must be positive
    error: APPOINTMENT_INVALID_REMINDER_OFFSET
  - field: cancelled_reason
    rule: required when cancelling
    error: APPOINTMENT_CANCEL_REASON_REQUIRED
  - field: revision
    rule: when supplied, must equal the stored revision
    error: APPOINTMENT_REVISION_CONFLICT

stateMachine:
  initial: booked
  states:
    - booked
    - cancelled
    - completed
    - no_show
  transitions:
    - from: booked
      to: booked
      trigger: reschedule
      guard: new slot is free, start_at is in the future, revision matches
    - from: booked
      to: cancelled
      trigger: cancel
      guard: cancelled_reason provided
    - from: booked
      to: completed
      trigger: complete
      guard: start_at has passed
    - from: booked
      to: no_show
      trigger: record_no_show
      guard: start_at has passed

workflows:
  - name: Book an appointment
    trigger: Requester submits a booking request
    actor: Requester
    steps:
      - Validate the time range, time zone and participants
      - Ask Calendar whether the slot is free for every participant
      - In one atomic operation, check for overlapping active appointments and persist the appointment with status = booked and revision = 0
      - Schedule one reminder per offset whose dispatch time is still in the future
      - Emit appointment.booked
    outcome: The appointment holds its slot and its future reminders are scheduled.
  - name: Reschedule an appointment
    trigger: Requester or Scheduler proposes a new time
    actor: Scheduler
    steps:
      - Verify the appointment is booked and the supplied revision matches
      - Validate the new slot and check availability with Calendar
      - In one atomic operation, check for overlaps, update the times, increase revision and record the previous times in history
      - Withdraw pending reminders and schedule new ones from the new start
      - Emit appointment.rescheduled
    outcome: The same appointment id now holds the new slot, with a higher revision.
  - name: Cancel an appointment
    trigger: Requester, Scheduler or an upstream policy cancels
    actor: Requester
    steps:
      - Verify the appointment is booked
      - Record cancelled_reason, cancelled_by and cancelled_at, and set status = cancelled
      - Withdraw pending reminders
      - Emit appointment.cancelled
    outcome: The appointment is retained as cancelled, its slot is released and no reminders fire.
  - name: Close out an appointment
    trigger: The start time has passed
    actor: Scheduler
    steps:
      - If the appointment took place, complete it and record completed_at
      - If a participant did not attend, record a no-show
      - Emit appointment.completed or appointment.no_show
    outcome: The appointment reaches a terminal state that reflects what happened.
  - name: Dispatch a reminder
    trigger: A scheduled reminder's dispatch time is reached
    actor: System
    steps:
      - Confirm the appointment is still booked and the reminder belongs to its current revision
      - Emit appointment.reminder_due
      - Notification delivers it to the participants
    outcome: Participants are reminded ahead of the appointment, and never about a superseded time.

functionalRequirements:
  - id: FR-1
    text: The service must let an authorised actor book an appointment for two or more participants.
    priority: must
  - id: FR-2
    text: The service must reject a booking or reschedule whose slot overlaps an active appointment for any participant, and the check must hold when requests arrive concurrently.
    priority: must
  - id: FR-3
    text: The service must allow only the transitions declared in the state machine and reject all others.
    priority: must
  - id: FR-4
    text: The service must schedule one reminder per offset, skip offsets already in the past, reschedule reminders when the time changes, and withdraw them when the appointment leaves booked.
    priority: must
  - id: FR-5
    text: The service must retain cancelled appointments and expose them to reads.
    priority: must
  - id: FR-6
    text: The service must emit a lifecycle event for every status change and every reschedule.
    priority: must
  - id: FR-7
    text: The service must store wall-clock times with an IANA time zone, and recompute derived instants for future appointments when the time zone database changes.
    priority: must
  - id: FR-8
    text: The service must accept an Idempotency-Key on book, reschedule, cancel, complete and record-no-show requests, and return the original result when a request is retried with the same key.
    priority: must
  - id: FR-9
    text: The service must reject a reschedule whose revision doesn't match the stored revision.
    priority: must
  - id: FR-10
    text: The service should let a deployment record no-shows automatically once a configurable grace period after start_at has passed with no completion.
    priority: should

nonFunctionalRequirements:
  - category: availability
    text: Read paths stay available when downstream consumers are unavailable, and downstream outages never block a booking.
  - category: scalability
    text: Reminder scheduling handles appointments booked months ahead without holding in-process timers.
  - category: observability
    text: Every status change and reschedule writes a structured audit entry with the actor, the previous value and the new value.
  - category: security
    text: A participant can read only appointments they take part in, unless they hold appointment.manage.
  - category: maintainability
    text: The service keeps its IANA time zone database current, because time zone rules change several times a year.
  - category: maintainability
    text: Industry-specific behaviour is additive. Core stays deployable with no industry layer present.

acceptanceCriteria:
  - id: AC-1
    given: a requester with appointment.write and two valid participants
    when: they book a free future slot
    then: an appointment is created with status booked and revision 0, and appointment.booked is emitted
  - id: AC-2
    given: an active appointment from 09:00 to 10:00 for a participant
    when: another booking from 09:30 to 10:30 is requested for the same participant
    then: the request fails with APPOINTMENT_SLOT_TAKEN and nothing is persisted
  - id: AC-3
    given: an active appointment from 09:00 to 10:00 for a participant
    when: another booking from 10:00 to 11:00 is requested for the same participant
    then: the booking succeeds, because the slots are back-to-back, not overlapping
  - id: AC-4
    given: two concurrent requests for overlapping slots for the same participant
    when: both are processed
    then: exactly one succeeds and the other fails with APPOINTMENT_SLOT_TAKEN
  - id: AC-5
    given: an appointment in status completed
    when: a cancel is attempted
    then: the request fails with APPOINTMENT_TERMINAL_STATE and the record is unchanged
  - id: AC-6
    given: a booking request 3 hours before start_at with reminder_offsets [24h, 2h]
    when: it is booked
    then: the booking succeeds, only the 2-hour reminder is scheduled, and no error is raised
  - id: AC-7
    given: a booked appointment at revision 2 with a pending reminder
    when: it is rescheduled with revision 2
    then: the id is unchanged, revision becomes 3, the old reminder is withdrawn, a new one is scheduled and appointment.rescheduled is emitted
  - id: AC-8
    given: a booked appointment at revision 3
    when: a reschedule is submitted with revision 2
    then: the request fails with APPOINTMENT_REVISION_CONFLICT and the appointment is unchanged
  - id: AC-9
    given: a booking request that succeeded
    when: it is retried with the same Idempotency-Key and the same body
    then: the original appointment is returned and no second appointment is created
  - id: AC-10
    given: a booked appointment whose start_at is in the future
    when: a Scheduler records a no-show
    then: the request fails with APPOINTMENT_NOT_YET_STARTED
  - id: AC-11
    given: an appointment at 09:00 Europe/Zurich, booked before a change to the zone's daylight saving rules
    when: the time zone database is updated
    then: start_time stays 09:00 and start_at is recomputed under the new rules
  - id: AC-12
    given: an appointment with a pending reminder
    when: it is cancelled
    then: the reminder is withdrawn and no appointment.reminder_due is emitted

decisions:
  - id: ADR-1
    decision: Cancellation is a status change, never a delete.
    rationale: Downstream modules keep references to appointment ids, and hard delete breaks billing and audit trails.
    alternatives: Hard delete with a tombstone table - rejected because it duplicates state and complicates reads.
    date: '2026-01-15'
  - id: ADR-2
    decision: Rescheduling changes the existing appointment and increases its revision instead of creating a successor.
    rationale: Attendance history and no-show statistics must follow one appointment across time changes, and the revision gives clients the same signal as iCalendar's SEQUENCE.
    alternatives: Cancel the original and book a linked replacement, as Cal.com and Calendly do - rejected because every reschedule then counts as a cancellation and history is split across records. Integrations with those systems map each revision to a new linked booking.
    date: '2026-01-15'
  - id: ADR-3
    decision: Reminders are delegated to a durable scheduler rather than in-process timers.
    rationale: Appointments are booked months ahead, and in-process timers don't survive deploys or restarts.
    alternatives: A periodic sweep over the table - viable, but adds polling latency and load at scale.
    date: '2026-01-20'
  - id: ADR-4
    decision: Availability, including working hours, buffers and minimum notice, is asked of Calendar rather than computed inside Appointment.
    rationale: Those rules legitimately differ per deployment and per resource. Keeping them out keeps the booking lifecycle identical everywhere.
    date: '2026-02-02'
  - id: ADR-5
    decision: Rescheduled is an event and a revision, not a status.
    rationale: A rescheduled appointment is still booked. A separate status forced a confirm step back to booked, and left completion and no-shows undefined for rescheduled appointments. iCalendar and Google Calendar have no rescheduled status either.
    alternatives: Keep rescheduled as a status - rejected for the reasons above.
    date: '2026-10-05'
  - id: ADR-6
    decision: Times are stored as wall-clock time plus an IANA time zone, with instants derived.
    rationale: For future events, an instant computed today can be wrong by the time the event happens if time zone rules change. The local time is what participants agreed to.
    alternatives: Store only UTC instants - rejected because a rule change silently moves future appointments. Store a fixed UTC offset - rejected because offsets carry no daylight saving rules.
    date: '2026-10-05'
  - id: ADR-7
    decision: No-shows are recorded by a Scheduler by default, with automatic recording after a grace period as an opt-in setting.
    rationale: Acuity Scheduling and Cal.com both record no-shows manually. Automatic expiry mislabels late arrivals and remote attendance, and a no-show is terminal and can carry fees.
    alternatives: Always record no-shows automatically when end_at passes - rejected for the reasons above.
    date: '2026-10-05'

openQuestions:
  - Should recurring appointments be modelled here, or as a separate Recurrence module that books individual appointments? iCalendar models a series as one event with a recurrence rule (RRULE).
  - Should core include a pending state for slots held while awaiting confirmation or payment? Cal.com holds bookings that need confirmation as pending, and iCalendar has a TENTATIVE status; Calendly's standard flow books immediately.
  - Should attendance be recorded per participant rather than for the whole appointment? Cal.com records absence separately for the host and each attendee.
  - How is a wrongly recorded no-show corrected, given that no_show is terminal?
  - Should overlap be checked per resource, such as a room or device, as well as per participant?

An appointment reserves a time slot between two or more participants. Booking,
rescheduling, cancelling, reminding and closing it out work the same way
whether it's a customer meeting a consultant, a candidate meeting an
interviewer, or two colleagues meeting each other.

What changes between industries is what must be true before a slot can be held
and what happens after it closes. Those obligations live in the industry
layers.

## Appointment holds the slot; Calendar decides if it's free

Appointment owns when people meet. It doesn't own who they are, whether they
can pay, what was discussed, or when they're available.

Availability is the boundary that matters most. Working hours, holidays,
buffers between appointments and minimum booking notice all differ between
deployments and between resources. Appointment asks Calendar whether a slot is
free instead of deciding for itself, so the booking lifecycle stays the same
everywhere and those rules live in one place.

## Ten o'clock to eleven doesn't clash with eleven to noon

A slot includes its start and excludes its end, the convention iCalendar and
Google Calendar both use. Back-to-back appointments are allowed; overlapping
ones aren't (BR-4).

The overlap check has to hold when two requests arrive at the same moment. A
check in application code followed by a separate insert lets both requests
succeed. The check and the write need to be one atomic operation, such as a
database exclusion constraint on the participant and the slot (FR-2, AC-4).

## Participants agree to a local time, so that's what is stored

An appointment at 09:00 in Zurich is stored as 09:00 plus `Europe/Zurich`.
The absolute instant is derived from them (BR-6).

Storing only UTC looks simpler, but it fails for future events. When a
government changes its daylight saving rules, an instant computed before the
change points to the wrong local time, and the appointment silently moves by an
hour. Keeping the wall-clock time means the derived instant can be recomputed
when the time zone database updates (AC-11).

## A reschedule changes the time, not the appointment

Moving an appointment keeps its id, records the previous time and increases its
revision (BR-3). Its attendance history stays on one record, and the revision
tells clients and calendar integrations that the time changed, the same signal
iCalendar carries in `SEQUENCE`.

Cal.com and Calendly take the other approach: they cancel the original
and book a linked replacement. Every reschedule then also counts as a
cancellation. Integrations with those systems can map each revision to a new
linked booking (ADR-2).

Rescheduling also isn't a status. A moved appointment is still booked, so it
can still be completed, cancelled or recorded as a no-show (ADR-5).

## A reminder that's already due is skipped, not refused

Each appointment can have several reminders. In a randomised trial, people
reminded both 3 days and 1 day ahead missed fewer appointments than people
reminded once.

When an appointment is booked closer to its start than a reminder's offset,
that reminder is skipped (BR-7). Rejecting the booking instead would make the
default 24-hour reminder block every same-day appointment.

## A no-show is recorded by a person, not inferred by a timer

Only someone at the appointment knows whether a participant is running late,
joined remotely or was seen elsewhere. Acuity Scheduling and Cal.com both
record no-shows manually, and so does this module by default (BR-8). A
deployment can opt in to recording them automatically after a grace period.

A no-show can't be recorded before the start time, and once recorded it's
final, like completion and cancellation (BR-5).

## Finished appointments never change

Completed, cancelled and no-show appointments are terminal. Consumers can
cache them without invalidation. Cancelling sets a status rather than deleting
the record, because billing, audit and analytics all reference the
appointment id (BR-2).
