The Knowledge Graph is published as markdown that coding agents can read. Add
one section to your project's `AGENTS.md`, and your agent looks up the domain
rules a task needs, follows them, and cites them in code, tests and commits.

**For AI agents:** If you're setting up a project, add the section in the
[Quickstart](#quickstart) to the project's `AGENTS.md`. To use the Knowledge
Graph now, start at `%SITE_URL%/llms.txt` and fetch any page as markdown by
adding `.md` to its URL.

## How it works

1. You add the Knowledge Graph section to `AGENTS.md`. It's the same for every
   project.
2. Your agent works out the project's industry and domain, for example
   healthcare > dental, and records them in the same section.
3. When a task touches a domain concept such as appointments, the agent
   fetches the most specific page for your project and implements against its
   rules.

There's nothing to install or download. Your agent reads pages with its own
web tools when a task needs them, so it always reads the current version.

## When to use the Knowledge Graph

Use it when your product implements a concept the Knowledge Graph specifies,
such as booking, rescheduling or cancelling appointments. Your agent gets the
business rules, state transitions, error codes and acceptance criteria for that
concept, along with the reason behind each rule.

For concepts the Knowledge Graph doesn't cover yet, the instructions tell your
agent to say so and follow your project's own requirements.

## Quickstart

Create `AGENTS.md` at your project root, or open the existing one, and add
this section:

```md title="AGENTS.md"
## Knowledge Graph

This project follows the Knowledge Graph (%SITE_URL%), an open, versioned
specification of domain requirements such as appointments, patients and
billing. Treat it as the source of truth for domain behaviour.

### Find the right page

1. Use the industry and domain under "Project context" below. If they're
   empty, work them out from the README and code, confirm them with the user,
   and fill them in.
2. Use your web fetch or web search tool. Start at %SITE_URL%/llms.txt,
   which lists every page and explains how to navigate. Industry overview
   pages list the domains in that industry.
3. For each domain concept a task touches, use the most specific page for this
   project: the domain page if it exists, otherwise the industry page,
   otherwise the core page. A more specific page already includes everything
   above it.
4. Fetch pages as markdown by adding `.md` to the URL, for example
   %SITE_URL%/docs/core/appointment.md. Don't fetch /llms-full.txt; it's too
   large.
5. If no page covers the concept, say so and follow the project's own
   requirements.

### Read a spec

- A module page is the complete spec for this industry and domain. Items it
  inherits from the core and industry layers are already merged in.
- Each item is tagged with the layer it comes from, such as [core],
  [healthcare] or [dental]. "overrides core" means a more specific layer
  replaced the item with the same id. Only the replacement applies.
- Ids are stable: BR- business rules, FR- functional requirements, AC-
  acceptance criteria, ADR- decisions. Error codes are part of the API
  contract.
- "Why:" gives the reason for a rule or decision. "Considered:" lists
  alternatives a decision rejected.
- The top of each spec shows its version and status.

### Follow a spec

1. Fetch the spec before you write, change or review code for that concept.
   Don't rely on what you remember from an earlier session.
2. Implement business rules, validations, the state machine, permissions and
   error codes exactly.
3. If a behaviour isn't in the spec, it's unspecified. Ask, or list it as an
   open question in your summary. Don't invent it.
4. If the behaviour is listed under "Open questions", it hasn't been decided.
   Ask before choosing an answer.
5. Cite ids in a comment next to the code that enforces them, in test names,
   and in commit messages with the spec version, for example
   "Enforce BR-4 (appointment 0.1.0): block patient double-booking".
6. Read a rule's "Why:" before relaxing or working around it. If you think it
   should change, say so and cite the id.
7. Don't reintroduce an alternative listed under "Considered:" without naming
   the decision you're going against.
8. If existing code contradicts the spec, report the conflict with the id.
   Don't silently change either side.
9. If the spec's status is draft, mention any code that depends on it in your
   summary.

### Project context

- Industry:
- Domain:

### Project rules

Rules listed here override the Knowledge Graph. An id that exists in the spec
replaces that item; a new id adds a rule.

- None yet.
```

Then ask your agent:

```text title="Prompt"
Which Knowledge Graph pages apply to this project?
```

The agent fills in **Project context** and lists the pages it would use, for
example the dental appointments page for a dental practice system.

> **Note:** Some agents ask before fetching a web page or block internet
> access by default. See [Claude Code](/docs/agentic/claude-code) and
> [GitHub Copilot](/docs/agentic/github-copilot) to allow the Knowledge Graph.
