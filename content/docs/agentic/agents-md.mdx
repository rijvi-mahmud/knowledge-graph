The [Quickstart](/docs/agentic#quickstart) section in `AGENTS.md` tells your
agent where the Knowledge Graph is, how to find the page a task needs, and how
to follow it. This page explains what the agent does with those instructions,
so you can predict its behaviour and adjust the section if you need to.

## Finding the right page

The Knowledge Graph is layered. **Core** pages describe a concept in
industry-neutral terms. **Industry** pages, such as healthcare, add what every
application in that industry needs. **Domain** pages, such as EHR, add what
only that kind of application needs. Each page shows its own items merged with
everything it inherits.

For a hospital EHR working on appointments, the agent:

1. Reads `%SITE_URL%/llms.txt` and finds the healthcare industry.
2. Fetches the healthcare overview and sees that EHR is one of its domains.
3. Fetches the EHR appointments page, which already includes the core and
   healthcare rules.

If the EHR domain has no appointments page yet, the agent uses the healthcare
page instead, and the core page (`%SITE_URL%/docs/core/appointment.md`) if
there's no healthcare page either. It never needs two pages for the same
concept.

The agent records the industry and domain under **Project context** in
`AGENTS.md`, so later sessions skip the first two steps.

## How a spec is structured

Each module page opens with its module, layers, version and status, then a
short guide on how to read it. The rest is grouped into rules and behaviour,
data, interface, requirements, terms and history:

```md title="core/appointment.md (excerpt)"
- module: appointment
- layer: core
- version: 0.9.0
- status: stable

**BR-4** A participant cannot have two active appointments whose slots
overlap. Slots are half-open, so an appointment ending at 10:00 and one
starting at 10:00 do not overlap.
  - Why: Double booking is a data-integrity failure, not a user preference ...
```

On an industry or domain page, every item also carries the layer it comes
from, such as `_[core]_` or `_[ehr (overrides core)]_`.

The same conventions apply to every module:

| In the spec | Meaning |
|---|---|
| `BR-`, `FR-`, `AC-`, `ADR-` ids | Business rules, functional requirements, acceptance criteria and decisions. Ids are stable, so code, tests and commits can cite them. |
| `[core]`, `[healthcare]`, `[ehr]` | The layer an item comes from. `core` items apply to every industry. |
| `overrides core` | A more specific layer replaced the item with the same id. Only the replacement applies. |
| `Why:` | The reason for a rule or decision, usually the failure it prevents. |
| `Considered:` | Alternatives a decision rejected. |
| Open questions | Behaviour that hasn't been decided yet. |
| `status` | `draft` specs can still change. `stable` specs change only through a new version. |

## What each instruction prevents

| Instruction | Without it, an agent may |
|---|---|
| Use the most specific page | Build from the core page and miss industry rules such as consent or eligibility |
| Fetch before changing code | Work from a stale memory of a spec that has since changed |
| Unspecified means ask | Fill a deliberate gap with a confident default. Specs leave behaviour open where practice varies between companies. |
| Open questions are undecided | Pick an answer the domain hasn't settled |
| Items are merged and tagged by layer | Read a `[core]` rule next to an `[ehr]` override as a conflict, or "fix" the override back to the core behaviour |
| Cite ids with the spec version | Make changes nobody can trace back to a requirement or to the version it was built against |
| Read `Why:` first | Simplify away a rule that prevents a costly failure |
| Respect `Considered:` | Reintroduce an approach a decision already rejected |
| Report conflicts | Silently rewrite working code, or silently ignore the spec |

## Project context and project rules

The last two parts of the section belong to your project. After the agent
fills them in, they look like this:

```md title="AGENTS.md"
### Project context

- Industry: healthcare
- Domain: ehr

### Project rules

Rules listed here override the Knowledge Graph. An id that exists in the spec
replaces that item; a new id adds a rule.

- **BR-4** Hygienists may not be double-booked. Why: Our hygiene chairs have no
  assistant cover.
- **BR-ACME-1** Same-day emergency slots are held until 10:00, then released.
  Why: Most emergency calls arrive before 10:00.
```

Project rules work the same way layers do in the Knowledge Graph: reusing an
id replaces the rule, and a new id adds one. Give each rule a reason, so the
next person or agent knows whether it still applies.

## Use in a monorepo

Keep the section in the root `AGENTS.md`. If packages belong to different
domains, add a short `AGENTS.md` to each one that sets its context:

```md title="packages/billing/AGENTS.md"
Follow the "Knowledge Graph" section of the root AGENTS.md. For code in this
package, the domain is revenue cycle management.
```

Cursor, GitHub Copilot and Claude Code use the `AGENTS.md` nearest to the file
being edited. A direct instruction in chat overrides it.

## Markdown endpoints

| URL | Returns |
|---|---|
| `/llms.txt` | How agents should use the Knowledge Graph, then every page with a markdown link and description |
| `/docs/<page>.md` | One page as markdown, merged with everything it inherits |
| `/llms-full.txt` | Every page in one file. Useful for research, too large to keep in context |

Requests to any docs URL with an `Accept: text/markdown` header also return
markdown. `/llms.txt` follows the [llms.txt proposal](https://llmstxt.org/);
`/llms-full.txt` is a common convention, not part of the proposal.
