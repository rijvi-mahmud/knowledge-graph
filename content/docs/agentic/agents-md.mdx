[AGENTS.md](https://agents.md/) is an open format for agent instructions.
Codex, Cursor, GitHub Copilot, Gemini CLI, Windsurf, Zed, Aider and many more
read it, and Claude Code can import it. If your team uses more than one tool,
this is the one file to maintain.

## The instruction block

Paste this into `AGENTS.md` once. It describes the Knowledge Graph and how to
work with it, not any one module, so it stays the same as you add specs. It
assumes the layout from [Use it in your project](/docs/agentic/use-in-your-project):
specs in `specs/`, listed in `specs/sources.txt`.

```md title="AGENTS.md"
## Domain specs

This project builds against domain specifications from the Knowledge Graph,
an open, versioned specification of domain requirements. They live in
`specs/`, one file per module (for example `specs/appointment.md`).
`specs/sources.txt` records which Knowledge Graph page each file came from.

### What a spec file is

- The complete requirements for one module in this product's industry and
  domain. Rules from the general layer (core), the industry layer and the
  domain layer are already merged into the one file.
- Each item is tagged with the layer it comes from, such as [core],
  [healthcare] or [dental]. "overrides core" means a deeper layer replaced the
  item with the same id; only the replacement applies.
- Ids are stable: BR- business rules, FR- functional requirements, AC-
  acceptance criteria, ADR- decisions. Error codes such as
  APPOINTMENT_NOT_FOUND are part of the API contract.
- "Why:" gives the reason for a rule or decision. "Considered:" lists
  alternatives that were rejected.

### When to read one

Before writing, changing or reviewing code for a module that has a spec, read
that spec, starting with its "How to read this spec" section. Do not rely on a
summary or on memory of an earlier version.

### How to follow it

1. Treat business rules, validations, the state machine, permissions and
   error codes as requirements. Implement them exactly.
2. If a behaviour is not in the spec, it is unspecified. Ask, or list it as an
   open question in your summary. Never invent it.
3. If the spec lists the behaviour under "Open questions", it is undecided.
   Ask before choosing an answer.
4. Cite ids in a comment next to the code that enforces them, in test names,
   and in commit messages (for example "Enforce BR-4: block patient
   double-booking").
5. Read a rule's "Why:" before relaxing or working around it. If you still
   think it should change, say so and cite the id. Do not change it silently.
6. Do not reintroduce an alternative a decision lists under "Considered:"
   without saying which ADR you are going against.
7. Where `specs/<module>.company.md` exists, it is this company's layer. An
   id it repeats replaces the spec's item with that id; new ids add rules.
8. When existing code contradicts the spec, report the conflict with the id.
   Do not silently change either side.
9. A spec with "status: draft" may still change. Flag code that depends on a
   draft rule in your summary.

### Never

- Edit files in `specs/` other than `*.company.md`. They are regenerated by
  `scripts/sync-specs.sh`, and edits are lost.
- Load a spec for a module this task does not touch. Each file is large.
```

## Why each line is there

- **"Merged" and the layer tags.** Without them, an agent seeing a `[core]`
  rule next to a `[dental]` rule may assume they conflict, or "fix" an
  override back to the core behaviour.
- **Unspecified means ask.** The single most valuable instruction. Specs are
  deliberately silent where practice varies; a confident invented default is
  worse than a question.
- **Cite ids.** Makes every change traceable to a requirement, and lets
  reviewers and later agents find all code for a rule.
- **Read "Why:" first.** Rules that look arbitrary usually prevent a specific,
  expensive failure. The reason is what stops an agent "simplifying" them away.
- **Don't edit `specs/`.** Agents like to fix things in place. A spec edit
  disappears on the next sync and leaves code that matches neither version.

## Monorepos

Put a short `AGENTS.md` in each package that builds against a different spec,
and keep the instruction block in the root file:

```md title="packages/scheduling/AGENTS.md"
This package implements `specs/appointment.md`. Follow the domain specs
section of the root AGENTS.md.
```

Most tools use the `AGENTS.md` closest to the file being edited, and a direct
instruction in chat overrides both.
