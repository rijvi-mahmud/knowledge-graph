title: Introduction
description: Complete, versioned domain requirements that coding agents fetch for each task instead of guessing, written once and inherited.
---

Most product requirements are not novel. Two teams building patient
registration will each work out the same duplicate checks, the same identity
rules and the same edge cases. A coding agent asked to build it will guess
them from its training data, confidently and differently each time.

The Knowledge Graph specifies that shared ground once, as complete and
versioned requirements that coding agents fetch and follow, and people can
read too. Each industry and kind of application adds only what's different.
It's currently focused on hospital software: the healthcare industry and the
electronic health record (EHR). The [EHR overview](/docs/healthcare/ehr) lists
which modules are specified, in the order they're built.

## Agents fetch the spec instead of remembering it

Every page is plain markdown: add `.md` to any page URL. Your agent starts at
[`/llms.txt`](/llms.txt), finds the page for your project's industry and
domain, and fetches only the sections a task needs, such as business rules or
validations. It cites every rule id it follows, and says so when a behaviour
isn't specified instead of inventing one.

One section in your project's `AGENTS.md` sets this up. See
[Agentic development](/docs/agentic).

## Knowledge is written once and inherited

A module is specified at up to three levels, each building on the one above:

- **Core** describes a concept in industry-neutral terms, such as the
  [core Appointment specification](/docs/core/appointment).
- **Industry** layers add what every application in an industry needs, such as
  [clinical appointments](/docs/healthcare/appointment) or
  [patient records](/docs/healthcare/patient) for healthcare.
- **Domain** layers add what one kind of application needs, such as
  [patients](/docs/healthcare/ehr/patient) and
  [appointments](/docs/healthcare/ehr/appointment) in an EHR.

A layer writes only what it adds. It can also replace an inherited item by
reusing its id, the way a subclass overrides a method. Every page shows the
merged result, with each item labelled by the layer it comes from, so an EHR
team, or its agent, reads one complete specification and still knows which
rules are universal. A module with no industry-neutral concept worth sharing,
such as patient records, starts at the industry level.

## Every module is a complete requirements specification

Each module follows ISO/IEC/IEEE 29148, the standard for software requirements
specifications, and is split into short pages in the sidebar:

| Folder | What it holds |
|---|---|
| Introduction | Purpose, scope, actors, assumptions and a context diagram |
| Variants | Pages for kinds of the module that differ in a few items, such as outpatient and inpatient appointments |
| Functions | Business rules, state machine, workflows, field validations and edge cases |
| Data | Data model, with the standard code system for every coded field, and relationships |
| External interfaces | API (with HTTP methods, paths and status codes), events, delivery guarantees, errors and contracts with other modules |
| Security | Permission matrix, permissions, privacy and retention |
| Requirements | Functional and performance requirements, quality attributes, design constraints and configuration |
| Reference implementation | One way to build it: storage design and implementation notes |
| Verification | Acceptance criteria and a traceability matrix |
| Supporting information | Glossary, decisions, risks, references and version history |

Every rule has a reason and a source, every requirement says how it's
verified, and every error code has an acceptance criterion with its HTTP
status. Ids such as BR-4 are links, and `pnpm check:specs` checks that each one
exists.

## Requirements say what, never how it's stored or coded

The HTTP interface is part of the requirements, because HTTP is a standard
rather than a vendor choice. So are standard codes, such as HL7, LOINC and
SNOMED CT, because other systems depend on them. Storage and code are not: the
Reference implementation folder shows one way to build a module, and no
requirement depends on it.

## Modules stay inside their own boundaries

A module specifies only its own job. Where it needs another module, its
Dependencies page lists only the contract between them: what it asks, and what
it gives. Appointments needs to know a patient exists, but not how patients
are registered.

## What varies is a setting, not a rule

Rules that differ between places or organisations are settings, never one
country's answer. Healthcare modules support the United States and the
European Union through a `jurisdiction` setting. Values that differ by US
state or EU member state, such as the age of majority or record retention,
are settings a deployment sets with legal advice.
