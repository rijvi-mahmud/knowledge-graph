---
title: Claude Code
description: Load the instructions every session, and each spec only when Claude works on the matching code.
---

The setup has two parts with different costs. The
[instruction block](/docs/agentic/agents-md#the-instruction-block) is short and
should load every session. Specs are around 10,000 tokens each and should load
only when Claude touches the module they describe.

## Load the instructions in CLAUDE.md

`CLAUDE.md` can import other files with `@path`, relative to the file that
contains the import. Import `AGENTS.md` so one file serves every tool:

```md title="CLAUDE.md"
@AGENTS.md
```

If you do not use `AGENTS.md`, paste the instruction block into `CLAUDE.md`
directly.

## Load each spec only where it applies

A rule in `.claude/rules/` with a `paths` field loads only when Claude reads or
edits a matching file. Add one per module, pointing at the code that
implements it:

```md title=".claude/rules/spec-appointment.md"
---
paths:
  - "src/scheduling/**"
---

Code under src/scheduling implements the appointment module. Read
specs/appointment.md before changing it, and follow the domain specs section
of AGENTS.md.
```

For a small project that builds against one or two modules, importing the
specs straight into `CLAUDE.md` is simpler, at the cost of loading them every
session:

```md title="CLAUDE.md"
@AGENTS.md
@specs/appointment.md
```

## Review a change against the specs

A skill packages a repeatable task Claude can run on request (`/spec-review`)
or on its own when the description matches:

```md title=".claude/skills/spec-review/SKILL.md"
---
name: spec-review
description: Review the current diff against the domain specs in specs/. Use when asked to check a change against requirements or rule ids.
---

1. Run `git diff` (or the diff the user names) and list the modules it touches.
2. For each module, read its file in specs/ and specs/<module>.company.md if
   it exists.
3. Report, citing ids:
   - rules, validations or state transitions the change breaks
   - behaviour the change adds that the spec does not specify
   - acceptance criteria with no matching test
   - error codes that differ from the spec
4. Do not edit code. End with the open questions the change depends on.
```

## Check it is working

Start a session and ask:

```text title="Prompt"
Which domain specs does this project use, and what does a [core] tag mean?
```

Claude should name the files in `specs/` and explain layer tags without
reading this site. If it cannot, the instruction block is not loaded; run
`/memory` to see which instruction files are in context.
