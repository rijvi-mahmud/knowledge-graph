---
title: Work with your agent
description: Prompts for building, testing and reviewing features against Knowledge Graph rule ids, and for handling spec changes.
---

Once `AGENTS.md` has the [Knowledge Graph section](/docs/agentic#quickstart),
your agent looks up specs on its own when a task touches a domain concept.
Referring to rule ids in your prompts makes its work precise and traceable.

## Build a feature

Name the concept, and the agent finds and follows the right page:

```text title="Prompt"
Add patient registration. Follow the Knowledge Graph spec for this project.
```

To implement specific rules, cite their ids:

```text title="Prompt"
Implement BR-H1 and BR-H3 from the Knowledge Graph patient spec.
```

The agent cites the ids in comments next to the enforcing code and in its
commit messages, with the spec version. To find every change to a rule later,
run:

```bash title="Terminal"
git log --grep BR-H3
```

## Check the agent's work against the spec

Before you accept a change, ask the agent to prove each rule it relied on:

```text title="Prompt"
For every Knowledge Graph id you cited in this change, fetch its section page
again and quote the line that supports what you did. Remove anything you
can't support.
```

The agent quotes the spec text next to each id, so you can see whether the
code follows the rule or a memory of it.

## Validate fields and use standard codes

Each spec's Validations page gives every field's rule and error code, and the
data model names the code system for each coded field:

```text title="Prompt"
Implement the patient field validations from the Knowledge Graph spec, with
the error codes it lists. Use the code systems named in the data model for
every coded field.
```

## Find what's missing

To compare existing code with a spec:

```text title="Prompt"
List every business rule in the Knowledge Graph patient spec that our code
doesn't enforce yet. For each, cite the id and the file where it should live.
```

To surface decisions the team still has to make:

```text title="Prompt"
Which open questions in the Knowledge Graph specs does this feature depend on?
```

## Generate tests from acceptance criteria

Acceptance criteria are written as Given / When / Then, so each one maps onto a
test:

```text title="Prompt"
Write one test per acceptance criterion in the Knowledge Graph patient spec.
Name each test after its id, and assert the error code and HTTP status where
the criterion names them. Don't add behaviour the criteria don't state.
```

## Review a change

To check a diff or pull request before merging:

```text title="Prompt"
Review this change against the Knowledge Graph specs for the concepts it
touches. Cite the rule id for every violation, and list behaviour the change
adds that the spec doesn't specify.
```

## Reach other modules through their contracts

Each module's Dependencies page lists what it asks of other modules and what it
gives them. Ask your agent to build against those contracts rather than
reaching into another module:

```text title="Prompt"
Which other modules does patient registration depend on, according to the
Knowledge Graph contracts? Build only against those contracts.
```

## Build for your jurisdiction

Rules that differ between the United States and the European Union, such as
record retention or response deadlines, depend on the `jurisdiction` setting.
Values that differ by state or member state, such as the age of majority, are
settings your team sets with legal advice.
Record it under **Project context** in `AGENTS.md`, and the agent applies the
right rules:

```text title="Prompt"
Our jurisdiction is eu. Which patient and appointment rules and settings
differ from the us defaults, and does our code follow the eu ones?
```

## Override a rule

When your product needs to differ from the Knowledge Graph, add the rule under
**Project rules** in `AGENTS.md`. Reuse the spec's id to replace a rule, or
use a new id to add one:

```md title="AGENTS.md"
### Project rules

- **BR-4** Oncology practitioners are never overbooked. Why: Infusion
  appointments need the practitioner's full attention.
```

Always give the reason. It's what tells a later reader whether the override
still applies.

## Handle spec changes

Your agent always reads the current version of a page, and commit messages
record the version each change was built against. When a spec's version moves
past the one in your history, check what changed:

```text title="Prompt"
The patient spec is now at a newer version than our commits cite. Fetch its
Version history, compare it with our code, and list rules we need to revisit.
```

The **Version history** section at the end of each spec lists what changed in
each version.
