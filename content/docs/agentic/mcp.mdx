The Knowledge Graph MCP server serves one company's specification to its
coding agents: the public specs your system uses, plus your company's own
rules on top. Every agent your team uses, such as Claude Code, Codex or
Cursor, connects to the same server and reads the same rules.

> **Note:** The MCP server isn't open for sign-up yet. This page describes
> what it does. To use the Knowledge Graph today, add the
> [AGENTS.md section](/docs/agentic#quickstart). It needs no account and
> works with any agent.

## When to use the MCP server

Use the [AGENTS.md section](/docs/agentic#quickstart) when the public specs
are enough: your agent fetches pages from this site and cites what it used.

Use the MCP server when your company has its own rules:

- **Your rules differ from the public ones.** You override a rule by its id,
  and add your own, with a `company` provenance label. Agents get the merged
  result, so they follow your version, not the public one.
- **You have modules the public specs don't.** A company-only module, such as
  patient outreach, sits next to the public modules and depends on them like
  any other module.
- **Your rules are private.** The server reads your specification from your
  own repository, and only a key for your workspace opens it.
- **Your team mixes agents.** Every agent reads the same source through one
  connection, so two developers on different tools build against the same
  rules.

## How agents use it

The server serves each of your projects' SRS, as your team writes it. An agent
first lists the projects, then reads one project's outline (its sections and
their ids) in one call, then reads only the sections the task needs.

| Tool | What it returns |
|---|---|
| `srs_list_projects` | Your projects with a published SRS: each one's id, name, latest published version and when, its size and its top-level sections. |
| `srs_outline` | One project's sections in document order, each with its id, title, heading level and size. |
| `srs_read` | One section as Markdown, with its subsections, or the whole SRS. Long answers come in pages. |
| `srs_list_items` | One project's items as data: user stories, requirements, rules, constraints, data entities and relationships, interfaces, events, errors, edge cases, acceptance criteria, open questions and more, each with its id, text, reason and how it's verified. Technical decisions and notes are marked as guidance, not requirements. |
| `srs_get_item` | One item by its id, with the acceptance criteria that verify it. |
| `srs_check_citations` | Whether each id an agent cites exists, with its kind and text. |
| `srs_search` | Lines that contain every word of a query, in one project or all, with the section each is in. |
| `srs_list_versions` | Every published version of one project's SRS: its number, the kind of change, a note on what changed, and when it was published. |

Agents read only published versions, and a version is published only when its items pass a structure check. The read tools return the latest one, or a published version an agent names, such as the one its code was built against.

The server tells every agent the same rules as the AGENTS.md section: read
the SRS for this task instead of working from memory, say "the SRS doesn't
specify this" instead of inventing a rule, and check every citation before
finishing. A project or section that doesn't exist comes back as an error that
names what does, never as a guess.
