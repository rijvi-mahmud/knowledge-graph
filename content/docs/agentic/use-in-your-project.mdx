---
title: Use it in your project
description: Pick your specs, vendor them into the repository, teach your agent to read them, and build against rule ids.
---

Steps 1 to 4 are one-time setup and take a few minutes. Steps 5 to 7 are how
you work from then on.

## 1. Pick the deepest page for each module you build

For every module your product touches, choose the most specific page that
matches your product. A deeper page already contains everything above it, so
you never need two pages for the same module.

| Your product | Module page to use |
|---|---|
| Matches a domain, such as a dental practice system | The domain page: `healthcare/dental/appointment` |
| In an industry, no domain page yet | The industry page: `healthcare/appointment` |
| Outside any listed industry | The core page: `core/appointment` |

Browse the sidebar, or read `/llms.txt` for the full list. If your domain's
overview lists a module as "Not yet specified", use the industry page for now
and switch when the domain page arrives.

## 2. List your specs in one file

Record which page each spec comes from. This file is the only thing you edit
by hand when you add a module or move to a deeper page.

```text title="specs/sources.txt"
# <page path on the Knowledge Graph>   <file in specs/>
healthcare/dental/appointment          appointment.md
```

Name each file after its module, so agents and people find `appointment.md`
without knowing which layer it came from.

## 3. Download them with a sync script

```bash title="scripts/sync-specs.sh"
#!/usr/bin/env bash
# Downloads every spec listed in specs/sources.txt from the Knowledge Graph.
# Set KG_URL to read from a self-hosted copy instead of the public site.
set -euo pipefail
KG_URL="${KG_URL:-%SITE_URL%}"

while read -r page file; do
  case "$page" in ''|\#*) continue ;; esac
  curl -fsSL "$KG_URL/llms.mdx/docs/$page/content.md" -o "specs/$file"
  echo "specs/$file <- $page ($(grep -m1 '^- version:' "specs/$file"))"
done < specs/sources.txt
```

```bash title="Terminal"
chmod +x scripts/sync-specs.sh
scripts/sync-specs.sh
git add specs scripts/sync-specs.sh
git commit -m "Add domain specs from the Knowledge Graph"
```

Each file is a merged spec: every inherited rule, field, endpoint and error,
tagged with the layer it came from. A spec is about 40 KB of markdown, roughly
10,000 tokens, which matters when deciding what to load on every session (see
step 4).

## 4. Teach your agent what the specs are

Downloading the files is not enough. The agent needs to know they exist, when
to read them, and what ids, layer tags and "unspecified" mean. Add the
[instruction block](/docs/agentic/agents-md#the-instruction-block) to your
`AGENTS.md`. It is written once for the whole project and does not change when
you add modules.

Then follow the setup for your tool, which mostly decides **when** a spec is
loaded: always, or only when the agent touches matching code.

- [Claude Code](/docs/agentic/claude-code)
- [Cursor](/docs/agentic/cursor)
- [GitHub Copilot](/docs/agentic/github-copilot)

## 5. Build against ids

Ids are the interface between you, the spec and the agent. Use them in
prompts:

```text title="Prompts that work"
Implement BR-4 and BR-D1 from specs/appointment.md.

List every business rule in specs/appointment.md that the code does not
enforce yet. For each, cite the id and the file where it should live.

Review this diff against specs/. For each violation, cite the rule id and the
failure it allows.

Which open questions in specs/appointment.md does this feature depend on?
```

An agent following the instruction block cites ids in code comments, test
names and commit messages, so `git log --grep BR-4` finds every change that
touched a rule.

## 6. Turn acceptance criteria into tests

Acceptance criteria are written as Given / When / Then, which maps directly
onto a test:

```text title="Prompt"
Write one test per acceptance criterion in specs/appointment.md. Name each test
after its id. Do not add behaviour the criteria do not state.
```

## 7. Add your company's rules without editing the specs

Vendored specs are regenerated by the sync script, so edits to them are lost.
Private company layers are not supported on this site yet. Until they are,
keep your additions in a file you own beside the spec, using the same id
style:

```md title="specs/appointment.company.md"
## Business rules

**BR-ACME-1** Same-day emergency slots are held until 10:00, then released.
- Why: most emergency calls arrive before 10:00.

**BR-4** (overrides the spec) Hygienists may not be double-booked.
- Why: our hygiene chairs have no assistant cover.
```

Re-using an id replaces that rule, exactly as layers do on this site. A new id
adds a rule. The instruction block already tells the agent that a
`<module>.company.md` file wins over the spec.

## Keep specs current

Re-run the sync script and review the diff like any other dependency update.
The `version` line at the top and the **Version history** section at the
bottom of each file show what moved. A rule whose id is unchanged but whose text
changed is the line to read carefully: code citing that id may now be wrong.
