A coding assistant asked to build cancellation, reminders or consent checks
will write something plausible. Plausible is the problem: it will not know that
a cancelled appointment is terminal, that consent gates completion rather than
booking, or why. The Knowledge Graph already specifies those rules, with their
reasons. This section shows how to put them in front of your assistant and how
to tell it what the specs mean.

## What your assistant gets

Every page on this site is also served as plain markdown. For a spec page, that
markdown is the **merged** spec: the page's own additions plus everything it
inherits, in one file.

A dental team does not load three files (core, healthcare, dental) and work out
which rule wins. It loads `healthcare/dental/appointment` and gets every rule
that applies to a dental practice, each tagged with the layer it came from:

```md title="specs/appointment.md (excerpt)"
- module: appointment
- layer: core > healthcare > dental
- version: 0.1.0
- status: draft

**BR-4** A patient cannot be double-booked, and an operatory cannot be unless
the practice allows overlap. ... _[dental (overrides core)]_
  - Why: A dentist runs several chairs while assistants and hygienists work ...
**BR-5** Once status is completed or cancelled, the appointment is terminal
and cannot transition further. _[core]_
**BR-H1** An appointment cannot transition to completed unless
consent_status = granted. _[healthcare]_
```

## Specs are written to be read by machines

The same conventions hold for every module, so one set of agent instructions
covers all of them.

| In the spec | What it tells the assistant |
|---|---|
| Ids: `BR-` rules, `FR-` requirements, `AC-` acceptance criteria, `ADR-` decisions | Stable handles. Cite them in code, tests and commits; refer to them in prompts. |
| Error codes such as `APPOINTMENT_NOT_FOUND` | Part of the API contract. Use them verbatim. |
| Layer tags: `[core]`, `[healthcare]`, `[dental]` | Where a rule comes from. Universal rules are tagged `core`. |
| `overrides core` | A deeper layer replaced the parent rule with the same id. Only the replacement applies. |
| `Why:` under a rule or decision | The failure the rule prevents. Read it before relaxing the rule. |
| `Considered:` under a decision | Alternatives already rejected. Do not reintroduce them silently. |
| Open questions | Known unknowns. Behaviour here is not decided. |
| `status: draft` or `stable` | Whether rules may still change. |

Above all: **anything not listed is unspecified.** Each spec opens with a "How
to read this spec" guide that says so, and your instructions should repeat it.
An assistant that fills gaps with invented behaviour is the failure this
project exists to prevent.

## Vendor the specs, don't link them

Instruction files (`AGENTS.md`, `CLAUDE.md`, Cursor rules, Copilot
instructions) load files from your repository, not URLs. So the recommended
setup is to download the specs you build against into a `specs/` folder and
commit them:

- **Reviewed.** A spec update arrives as a diff in a pull request, not as a
  silent change in agent behaviour.
- **Reproducible.** Every teammate and every agent run reads the same version.
- **Offline.** No network call, no rate limits, no dependency on this site
  being up.

[Use it in your project](/docs/agentic/use-in-your-project) walks through the
setup, including a script that keeps the folder in sync.

## Endpoints

| URL | Returns | Use it for |
|---|---|---|
| `/llms.txt` | Index of every page with its description | Finding the page for your product |
| `/llms.mdx/docs/<page>/content.md` | One page as markdown, merged with its parents | Vendoring into `specs/` |
| `/docs/<page>.md` | The same markdown, at a shorter address | Pasting a link into chat |
| `/llms-full.txt` | Every page in one file | One-off research. Too large to keep in context |

`<page>` is the page's path after `/docs/`. The dental appointment spec at
`/docs/healthcare/dental/appointment` is served at
`/llms.mdx/docs/healthcare/dental/appointment/content.md`. Links in
`/llms.txt` point at the HTML pages; add `.md` to any of them, or request it
with an `Accept: text/markdown` header, to get markdown.

`/llms.txt` follows the [llms.txt proposal](https://llmstxt.org/).
`/llms-full.txt` is a common convention, not part of that proposal.

### Which address to use

This site is served at [%SITE_URL%](%SITE_URL%), so the dental appointment
spec is at:

```text
%SITE_URL%/llms.mdx/docs/healthcare/dental/appointment/content.md
```

To pin a release or work offline, run your own copy. Set
`NEXT_PUBLIC_SITE_URL` to its public address, and every URL in these docs,
including the sync script's default, points at your copy:

```bash title="Terminal"
git clone https://github.com/rijvi-mahmud/knowledge-graph
cd knowledge-graph
pnpm install
pnpm dev                               # serves http://localhost:3000
```

### Live access

Assistants with a web-fetch tool can read `/llms.txt` and individual pages
directly, which is useful for exploring which modules exist. Do not rely on it
for building: results change when the site changes, and nothing records which
version the code was written against. There is no MCP server yet.
