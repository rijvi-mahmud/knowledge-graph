The [Quickstart](/docs/agentic#quickstart) section in `AGENTS.md` tells your
agent where the Knowledge Graph is, how to find the page a task needs, and how
to stay grounded in it. This page explains what the agent does with those
instructions, so you can predict its behaviour and adjust the section if you
need to.

## Finding the right page

The Knowledge Graph is layered. **Core** pages describe a concept in
industry-neutral terms. **Industry** pages, such as healthcare, add what every
application in that industry needs. **Domain** pages, such as EHR, add what
only that kind of application needs. Each page shows its own items merged with
everything it inherits. Some modules, such as Patients, start at the industry
level because there's no neutral concept worth sharing yet.

For a hospital EHR working on patient registration, the agent:

1. Reads `%SITE_URL%/llms.txt` and finds the healthcare industry.
2. Fetches the healthcare overview and sees that EHR is one of its domains,
   and the EHR overview, which lists the modules specified so far.
3. Fetches the sections of the EHR Patients page the task needs, which already
   include the healthcare patient record rules.

If the domain has no page for a concept yet, the agent uses the industry page,
then the core page. It never needs two pages for the same concept. The agent
records the industry, domain and jurisdiction under **Project context** in
`AGENTS.md`, so later sessions skip the first two steps, but it still reads
`llms.txt` to see modules added since.

## Staying in your industry and domain

Different domains can specify a module with the same name from different
purposes. One domain's appointments may be about booking, another's about
when a visit becomes billable. Rules from the wrong domain look plausible
and are wrong for your product, so the instructions keep the agent on your
project's path:

- **Only your path.** The agent uses core pages, your industry's pages and
  your domain's pages: URLs under `/docs/core/`, `/docs/<industry>/` and
  `/docs/<industry>/<domain>/`.
- **Never a sibling.** A page from another industry or domain is never used,
  even when it has the module the agent is looking for. If your domain has no
  page for it, the agent falls back up your own path, to your industry and
  then core.
- **Check the identity.** Every module page opens with "Module identity" and
  its layer, such as `healthcare > ehr`. The agent checks it against
  **Project context** before using the page. A web search can land on any
  page, so this check is what catches a mismatch.

## Fetching only what a task needs

A module page's markdown is its complete spec, merged across layers, and the
EHR pages are well over 100 KB. Each section is also its own page of a few
KB, so the agent fetches the ones a task needs:

| Task | Sections to fetch |
|---|---|
| Implement a feature | `functions/business-rules`, `functions/validations`, `data/data-model`, `interfaces/operations`, `interfaces/errors` |
| Write tests | `verification/acceptance`, `functions/edge-cases` |
| Call another module | `interfaces/dependencies`, then the other module's page if it exists |
| Set up storage | `data/data-model`, then `reference-implementation/tables` as one non-normative option |
| Configure a deployment | `requirements/settings` |

Small pages matter for accuracy as well as size. Many agents' fetch tools
pass long pages through a smaller model that summarises them, and a summary
can drop or blur exactly the detail a rule depends on.

## Staying grounded

These instructions keep the agent's domain decisions tied to text it fetched,
following [Anthropic's guidance on reducing hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations):

| Instruction | What it does |
|---|---|
| Fetch the page for this task, in this session | Replaces memory, which may be from an older version or another project, with the current spec |
| Unlisted means unspecified | Gives the agent permission to say it doesn't know, instead of filling a gap with a plausible default |
| Cite id, version and URL | Makes every claim checkable by you, and traceable later |
| Check each cited id before finishing | Catches a claim the agent can't support from what it fetched |
| Prefer section pages when the fetch tool summarises | Keeps the agent quoting the spec rather than a summary of it |

## How a spec is structured

Each module page opens with its module, layers, version and status, then a
short guide on how to read it. The rest follows ISO/IEC/IEEE 29148: functions,
data, external interfaces, security, requirements, a non-normative reference
implementation, verification and supporting information.

```md title="healthcare/ehr/patient/functions/business-rules.md (excerpt)"
**BR-H3** An identifier's system and value belong to at most one record that
is active or inactive. _[healthcare]_
  - Why: Two people with the same medical record number means a scan or a
    lookup can open the wrong person's record.

**BR-E1** Every patient gets an MRN from mrn_system at registration,
including its check digit. ... _[ehr]_
```

The same conventions apply to every module:

| In the spec | Meaning |
|---|---|
| `BR-`, `FR-`, `AC-`, `EC-`, `CON-`, `AS-`, `DG-`, `ADR-` ids | Business rules, functional requirements, acceptance criteria, edge cases, design constraints, assumptions, delivery guarantees and decisions. Ids are stable, so code, tests and commits can cite them. A layer letter, such as `BR-H3` or `BR-E1`, shows where the item was written. |
| `[core]`, `[healthcare]`, `[ehr]` | The layer an item comes from. |
| `overrides` | A more specific layer replaced the item with the same id. Only the replacement applies. |
| Validations | Each field's rule and the error code it returns. |
| `codes:` on a field | The standard code system to use, such as HL7 v2 Table 0203, LOINC or SNOMED CT. |
| Operations and errors | HTTP method, path and success status, and each error's HTTP status. |
| Acceptance criteria | Given / When / Then, one test each, naming the ids they verify. |
| `Why:` | The reason for a rule or decision, usually the failure it prevents. |
| `Considered:` | Alternatives a decision rejected. |
| Open questions | Behaviour that hasn't been decided yet. |
| `status` | `draft` specs can still change. `stable` specs change only through a new version. |
| Contract (on Dependencies) | What the module asks of another module or gives it. The other module's internals are out of scope. |
| Variant | A kind of the module, such as inpatient, with its own page listing the items that apply only to it. |
| Compliance (`CMP-`) | Each legal obligation that applies, such as a HIPAA or GDPR provision, how the spec meets it, and whether it falls to this module, the deployment or another module. |
| Settings | What varies by deployment, such as `jurisdiction` (us or eu), retention or the age of majority. |
| `US only:`, `EU only:` | The item applies only in that jurisdiction, such as a HIPAA or GDPR duty. Unmarked items apply everywhere. |
| Reference implementation | Storage design and implementation notes. Non-normative: one way to build it. |

## What each instruction prevents

| Instruction | Without it, an agent may |
|---|---|
| Use the most specific page | Build from a core page and miss industry rules such as identity checks or retention |
| Stay on your path, check the identity | Follow another domain's rules for a module with the same name, because a search landed there |
| Fetch sections, not the whole site | Load more than fits in context, or get a lossy summary |
| Open questions are undecided | Pick an answer the domain hasn't settled |
| Items are merged and tagged by layer | Read a `[core]` rule next to an `[ehr]` override as a conflict, or "fix" the override back |
| Use the named codes | Invent local codes that no other system understands |
| Read `Why:` first | Simplify away a rule that prevents a costly failure |
| Respect `Considered:` | Reintroduce an approach a decision already rejected |
| Report conflicts | Silently rewrite working code, or silently ignore the spec |
| Use contracts | Rebuild another module's rules inside this one, so the two drift apart |
| Apply the jurisdiction, skip other jurisdictions' items | Follow US rules for an EU deployment, or the other way round |

## Project context and project rules

The last two parts of the section belong to your project. After the agent
fills them in, they look like this:

```md title="AGENTS.md"
### Project context

- Industry: healthcare
- Domain: ehr
- Jurisdiction: us

### Project rules

Rules listed here override the Knowledge Graph. An id that exists in the spec
replaces that item; a new id adds a rule.

- **BR-4** Oncology practitioners are never overbooked. Why: Infusion
  appointments need the practitioner's full attention.
- **BR-ACME-1** Same-day urgent slots are held until 10:00, then released.
  Why: Most urgent requests arrive before 10:00.
```

Project rules work the same way layers do in the Knowledge Graph: reusing an
id replaces the rule, and a new id adds one. Give each rule a reason, so the
next person or agent knows whether it still applies.

## Use in a monorepo

Keep the section in the root `AGENTS.md`. If packages belong to different
domains, add a short `AGENTS.md` to each one that sets its context:

```md title="packages/billing/AGENTS.md"
Follow the "Knowledge Graph" section of the root AGENTS.md. For code in this
package, the domain is revenue cycle management.
```

Agents read the nearest `AGENTS.md` in the directory tree, so the closest one
takes precedence. A direct instruction in chat overrides it.

## Markdown endpoints

| URL | Returns |
|---|---|
| `/llms.txt` | How agents should use the Knowledge Graph, then every page with a markdown link and description |
| `/docs/<page>/<group>/<section>.md` | One section of a module, such as `functions/validations`. Usually a few KB |
| `/docs/<page>/<variant>.md` | One variant of a module, such as `inpatient` |
| `/docs/<page>.md` | One module page: the complete spec, merged with everything it inherits. Can pass 100 KB |
| `/llms-full.txt` | Every page in one file. For research, too large to keep in context |
| `/openapi/<page>.json` | One module's endpoints, success statuses and error codes as OpenAPI 3.1, generated from the spec. The spec page stays normative |
| `/versions/<page>/<version>.md` | A module's merged spec as published at that version, for comparing with what your code cites. Listed under Optional in `/llms.txt` |

Requests to any docs URL with an `Accept: text/markdown` header also return
markdown. Markdown responses carry `charset=utf-8` and a canonical link to
the HTML page. `/llms.txt` follows the [llms.txt proposal](https://llmstxt.org/);
`/llms-full.txt` is a common convention, not part of the proposal.
